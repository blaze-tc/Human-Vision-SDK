# Runtime Prefab Android RTSP 同帧显示验收

## 实现

- Android 的高清预览和模型图片走独立分支。预览为识别让行时，该帧的高清图片可能跳过。启用 `HumanVisionRuntimeView.UseAnalysisFrameForMatchedPreview` 后，右侧合成使用已提交识别的同一张 `512×288` 图片，按来源、代次和结果帧号配对。左侧显示最高 `1920×1080` 的独立预览。
- 快照纹理拥有独立生命周期。识别原始纹理的复制租约通过实际栅栏退役，CPU 回读继续使用自己的快照。发布、快照观察、原生归还和回读均可按原生顺序号与统一帧号关联。记录仍在占用的原生槽位以及归还结果。
- Runtime Prefab Acceptance 默认启用模型图片配对，并提供 180 秒验收与 JSONL 导出。日志分别记录解码、识别输入、有效骨骼、同帧合成、最大配对间隔及设备可读取的频率和温度。
- 公开 Android Input 的默认转换调度与本地验收一致。公开 ABI 保留 `HV_Input_ProbeRtsp`；本地验收 APK 额外包含对照实验专用的预览步长开关。公共 SDK 与私有 RK3588 模型和厂商库独立交付。

## 同素材真机对照

一加 9 Pro。Android MediaCodec、Vulkan 输入、Unity 30 FPS 和与 RKNN 共用的 CPU 回读链路。两份 APK 对每个分辨率读取完全相同的本地 H.264 25 FPS 循环素材。1080p 由 4K 素材生成，镜像、模型输入和识别区域一致。4K 记录 144 秒，1080p 记录 84 秒。帧率比较用无录屏窗口，画面闪空用独立连续录屏窗口。

| 码流 | 硬解 FPS 旧 → 新 | 原生识别发布 FPS 旧 → 新 | 实际提交 FPS 旧 → 新 | 有效结果同帧配对比例 旧 → 新 |
| --- | ---: | ---: | ---: | ---: |
| 3840×2160 | 24.98 → 24.98 | 24.90 → 24.89 | 22.21 → 24.15 | 96.2% → 100% |
| 1920×1080 | 24.99 → 24.98 | 24.93 → 24.95 | 24.38 → 23.89 | 97.6% → 99.8% |

四组无空识别槽计数为零。新版的 4K 和 1080p 各录屏约 30 秒，共分析 1,798 个显示帧，左侧有画面时右侧闪空次数为零。相邻两次右侧画面更新的 P95 间隔均约 100 ms。

分辨率对照中的新版设备起始温度较高。4K/1080p 的 CPU 推理中位耗时从 53.82/54.15 ms 增至 65.35/64.83 ms。对照同时记录了设备热状态和实际送入模型的帧率，以区分模型运算与预览调度。

在更接近的温度下复核 4K 默认调度，旧版与新版的起始电池温度分别为 39.7°C 和 39.4°C。CPU 推理中位耗时为 64.25 和 65.58 ms，有效骨骼为 14.91 和 15.46 FPS，右侧有效同帧骨骼为 14.23 和 15.41 FPS。原生识别发布为 24.41 和 24.89 FPS。

另用本地测试开关把 4K 的高清预览采样步长设为 3，复现高清同帧候选稀疏的场景。两个版本的高清预览约 8 FPS。

| 4K 高清预览压力对照 | 旧版 | 新版 |
| --- | ---: | ---: |
| 原生识别发布 FPS | 24.91 | 24.89 |
| 实际提交 FPS | 24.12 | 24.08 |
| 有效同帧骨骼 FPS | 5.70 | 14.98 |
| 连续录屏最大右侧更新间隔 | 665.34 ms | 133.57 ms |

录屏按源画面内可识别的时间标记统计。旧版 454 个显示帧中有 12 帧出现等待画面，新版 458 个显示帧均可识别右侧源画面标记。

- 架构和组件边界、两个 UPM 包的文件闭包、GUID、Git 换行及原生依赖校验通过。对应分支的本地 RK3588 三档资源包通过 62 个已索引资源的校验。

上述真机数据来自一加的 CPU 回读对照。RK3588 的 NPU 推理帧率和热机表现由对应设备数据确认。
