## 5. 正式项目应怎样补测

1. 记录设备、CPU/GPU、系统、Unity、SDK/Input tag和lock hash、构建模式、APK/EXE及运行数据hash、实际Profile、质量、人数、区域、源编码/尺寸/FPS、镜像。
2. 先单人Camera确认基本识别；再按平台和源运行Video、RTSP，并分别测试1/2/4/6/8人，不把MaxBodies替代实际人数。
3. 动作测试选Skeleton，关闭键盘混合影响；测试静止、仅摆臂、仅抬腿、完整跑步、一次跳跃、回落、换人、出区、遮挡和失去跟踪。
4. 固定配置后预热10秒，至少连续采集40秒；另做较长稳定性/热运行，记录完整原始结果。测试期间不修改区域/质量/源；若修改则标记本次无效并重测。
5. 每个新的ResultSequence最多计一次；零身体/部分骨骼不能丢掉；按参与者TrackId及必需有效关节点分别统计更新数与掉点。
6. 记录结果年龄P50/P95、阶段耗时、源FPS、结果FPS、各参与者有效完整更新FPS、丢帧、ID换人、暂停/重连、崩溃及热降频。
7. Android测试前后台、拒绝权限、网络断开再连、Vulkan能力失败、保存重启和系统导出ZIP。Windows测试相机占用、失焦、媒体缺失及独立构建。

## 6. 正式项目日志能证明什么

`statistics.csv`包含状态、源率、项目接受的新结果率、SDK计数、身体数、阶段时间、读回丢帧/错误、结果年龄与帧ID。`fresh_result_fps`由项目`ObservationCount`差分得出：回调要通过Running、序号去重和CanPresent检查；后续年龄/区域过滤前已增加计数，因此不是最终有效动作观察数，更不是每人FPS。

`skeleton.jsonl`默认每区域0.2秒才记一次（约5Hz上限），并且详细日志主要在Setting启用。即使把间隔设成最小0.02秒，也没有声明无丢失的全速原始采集保证；队列丢弃和节流都要记录。严格验收应在`ResultUpdated`/原生观察边界建立不重计、可检查溢出的采集器，并按每人每点有效性统计。

`DetectionMs/PoseMs/TrackingMs`在Runtime模式分别映射预处理/推理/后处理；不要据旧字段名断言YOLO存在独立检测器耗时。`ProcessedFrames`在该模式映射BodySequence。源帧、身体结果、显示采样分别计数。
