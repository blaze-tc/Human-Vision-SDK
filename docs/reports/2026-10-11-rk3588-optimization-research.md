# RK3588 骨骼帧率优化研究（2026-10-11）

本次为公开资料、当前源码、已有实测记录的交叉研究；没有新的 RK3588 实测，未修改运行代码。研究结论是仍有优化空间，最值得推进的是 NPU 专用导出图与精度合格的混合量化，同时完成供帧、缓存同步和输出搬运优化。20–25 FPS 是验收目标，不能从官方模型跑分直接推导本 SDK 已能达到。

## 1. 已有证据与边界

实测基线 `session-20261010-080649-482-b1084e4c`：发布约 11.83 FPS，完成约 8.43 FPS；SDK 总耗时均值约 51.95 ms。另一个周期采样集合的 RKNN 输入/执行/输出均值分别为 14.24 / 27.74 / 4.45 ms。不可用不同采样集合相减计算未记录的开销。回读生命周期约 136.61 ms 含排队和 Unity 回调，不能称为纯拷贝耗时。

这些数据说明供帧和单次处理成本同时存在问题。NPU 执行不是全部耗时，低利用率也不能单独解释瓶颈。日志的三核请求 `core_mask=7`、约 1 GHz 频率意味着“开启三核/提高利用率”不是尚未实施的确定提速方案；实际核调度仍需设备性能报告确认。

当前已完成、但尚缺 RK3588 实测的优化：独立有界 GPU 快照、GPU 复制结束释放解码纹理、通过像素检查后按模型尺寸回读、每帧坐标及会话身份、APK 视频缓存播放、原生 FP16 输入与可复用 FP32 输出资格检查。不能将这些再作为本次新发现。

详细依据：[上一轮实现和验证](2026-10-11-rknn-native-io.md)、[先前精度实验](2026-10-10-rk3588-field-repair.md)。

## 2. 官方性能对照说明什么

Rockchip Model Zoo 的公开表格列出 YOLOv8n-Pose，输入 640×640，INT8，RK3588 **单核 55.9 FPS**，约 17.9 ms/次。条件是平台最高 NPU 频率，统计模型推理，不包含预处理和后处理。它与我们的 512×288 恢复图、非量化模型、Unity 全链路不是同一测试，不能按像素比例换算速度，也不能承诺 Unity 达到 55.9 FPS。[官方性能表及条件](https://github.com/airockchip/rknn_model_zoo#model-performance-benchmarkfps)

更关键的是，官方 Pose 转换脚本对 RK3588 的量化路径使用 hybrid_quantization_step1/step2，并指定三个关键点分支的混合精度范围。表中标记 INT8 不代表整个 Pose 网络都必须强制 INT8。官方还提供 RKNN 专用导出头，而非直接沿用通用部署输出。[官方转换脚本](https://github.com/airockchip/rknn_model_zoo/blob/main/examples/yolov8_pose/python/convert.py)、[官方导出头](https://github.com/airockchip/ultralytics_yolov8/blob/main/ultralytics/nn/modules/head.py)

因此，公开资料支持继续研究模型部署方式；不支持把当前低帧率判定为 RK3588 硬件的固定上限。

## 3. 新增优化机会

### A. NPU 专用导出图与混合量化：较大的潜在收益

当前 ONNX 由 NCNN 已融合、FP16 存储的权重恢复到 FP32，并非原始训练模型直接导出。本次用固定 Docker 环境检查图：72 个 Conv、63 个 Sigmoid、63 个 Mul、6 个 Reshape、6 个 Transpose。两个输出为 `[1,3024,65]` 和 `[1,3024,51]`。

这些节点数量不等于设备实际执行数量；编译器可能融合或消除它们。目前没有证据证明某个 Transpose 或 SiLU 已回落 CPU，不能仅靠图结构下结论。

建议建立独立 NPU 候选模型包：优先从可追溯原始权重导出，按官方部署方式调整输出头；若原始权重不可得，先对固定恢复图做受控的尾部布局实验。按设备逐层耗时确认格式转换或算子回退，再改动对应节点。不能把官方节点名称照抄到当前恢复图。

量化不能简单重试此前参数：99 帧单一视频校准的全 INT8 已超过 3 px 关节偏差门槛；三个混合量化候选中，七人最大偏差分别为 10.223、10.083、4.826 px，均被拒绝。下一次应使用更多独立场景、距离、遮挡、人数、曝光和动作的校准数据，并保留独立验证集；检查逐层误差后选择保留浮点的范围。增加数据本身不保证通过，必要时才评估有训练数据支持的量化感知训练。

同模型 I/O 优化继续要求完整输出等价。改变权重/量化/输出语义的模型候选须使用明确的精度合同、逐人匹配、漏检和误检检查，不能靠放宽原有精度门槛换取速度。

### B. 明确缓存同步责任：可直接做对照的增量优化

当前 `runtime/plugins/backend/rknn/rknn_android_vendor.cpp` 的候选上下文以 flags=0 初始化，同时显式执行输入 TO_DEVICE 和输出 FROM_DEVICE 同步。官方 API 提供关闭默认输入/输出缓存维护的标志，允许应用自行负责同步。因此存在重复维护缓存的可能，但重复是否发生、成本多大必须实测。

候选方案：只在共享内存路径关闭对应自动维护，保留显式同步；仍使用 outputs_get 的路径不能关闭其默认输出维护。保持原基线、资格检查和错误回退。绝不能直接删除缓存同步或 GPU/RGA 完成栅栏。[RKNN API 定义及限制](https://raw.githubusercontent.com/airockchip/rknn-toolkit2/master/rknpu2/runtime/Android/librknn_api/include/rknn_api.h)

### C. 原生输出与后处理：继续减少转换及搬运

两个密集 FP32 输出每帧共 350,784 个值，即 1,403,136 字节。当前共享输出仍请求 FP32，并复制到原有缓冲；“共享内存”不等于没有输出转换和复制。

可查询原生输出类型、布局及步幅，尝试原生 FP16 输出，再在消费者侧一次转换至现有 FP32 合同。仅在原生输出确为 FP16 时，紧密有效数据才约减半；实际分配还包括对齐。更进一步可让私有后处理直接消费原生布局，但需要独立精度与生命周期验证，不改变公共 ABI。

旧输出获取约 4.45 ms，故这属于减少几毫秒级预算的候选，不能单独承诺把 8 FPS 提到 25 FPS。新图也不能仅靠输出变小就推定更快。[原生张量查询 API](https://raw.githubusercontent.com/airockchip/rknn-toolkit2/master/rknpu2/runtime/Android/librknn_api/include/rknn_api.h)

### D. 解码缓冲经 RGA 到 NPU：架构上可减少回读依赖

目标是解码后分为独立预览和分析消费者；分析通过 RGA 缩放/颜色转换进入复用的 RKNN 输入，绕过 Unity GPU→CPU 回读。官方 RGA FAQ 建议通过缓冲池及复用导入句柄减少反复映射开销。[RGA 官方 FAQ](https://github.com/airockchip/librga/blob/main/docs/Rockchip_FAQ_RGA_CN.md)

当前解码缓冲为 AIMAGE_FORMAT_PRIVATE，不能假定为线性 NV12，也不能任取 native_handle 的 fd。实际 gralloc 格式、modifier、步幅、导入能力和驱动必须在 RK3588 验证；RGA 输出还需检查颜色范围、插值、镜像及坐标。当前保持未启用，现有独立快照路径作为回退。[项目 RGA 评估](../maintenance/RK3588_RGA_ASSESSMENT.md)

### E. 多上下文/核分配流水线：有条件的吞吐实验

当前已请求三核。可以对照单上下文三核与多个独立上下文分核，但 DDR 竞争、内存增量和热稳定性可能抵消收益。队列必须有界，保持 source/generation/frame/timestamp/transform 元数据，拒绝乱序迟到结果。提高吞吐不保证降低单帧延迟。

RKNN 的 ASYNC 标志可能返回前一帧结果，不能只打开标志后仍把结果当当前帧。逐层性能采集本身有开销，应另开诊断阶段，正式帧率测试关闭。[官方异步与性能采集说明](https://raw.githubusercontent.com/airockchip/rknn-toolkit2/master/rknpu2/runtime/Android/librknn_api/include/rknn_api.h)

### F. MediaPipe/RTMPose 类路线：作为人数受限的独立候选

Google 文档说明视频和实时流可利用跟踪避免反复触发检测；可借鉴“低频重定位 + 每张新帧执行关键点网络”的设计。不能用跟踪外推冒充新骨骼推理。当前整图多人模型不能通过简单跳过检测来保留独立姿态计算，需要管线及模型改变。[MediaPipe 官方说明](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/python)

MMPose 官方有 RTMPose 的 RKNN 部署配置，可作为技术可行性线索；没有由此得到本机帧率保证。逐人裁剪姿态模型的成本随人数增长，单人快不代表 4–8 人快，不能把它作为默认替换方案。[MMPose 部署文档](https://github.com/open-mmlab/mmpose/blob/main/docs/en/user_guides/how_to_deploy.md)

## 4. 20–25 FPS 的工程预算与一次安装验收

连续 20/25 个新结果每秒对应 50/40 ms 的结果间隔。单 worker 串行处理时，如果 run 仍为约 27.74 ms，那么 25 FPS 留给其余处理及串行空档的预算仅约 12.26 ms。供帧可以与推理重叠；因此不能直接将所有异步阶段相加预测吞吐。

建议将模型执行约 18–22 ms、输入输出和前后处理合计约 8–12 ms 作为优化预算，给调度留下余量。这是开发目标，不是测得值、官方保证或帧率预测。

输入必须实际提供足够的新帧。上一轮 OnePlus 的电脑 RTSP 对照预览约 15 FPS，不可能从该源验收 25 个独立新帧结果；这不证明 RK3588 的另一台摄像头同样只有 15 FPS。应以源 PTS、解码与发布计数分别核对，不能只看编码器标称帧率。

离线先完成固定帧的像素、数值、姿态精度和四档分辨率/镜像/重连/迟到结果回归。只将通过门槛的候选纳入同一个 APK。设备自动执行：输入速率核验 → 本地视频及 RTSP 预览 → 基线/候选/重复基线 → 长时热稳定性测试。模型性能与端到端性能分别报告，避免归因混淆。

报告每个人每秒来自不同源帧的有效完整骨骼数、帧间隔分布、局部结果年龄、丢帧/重帧/漏检、各阶段 p50/p95；RTSP 端到端年龄若没有时钟同步，不得假装知道摄像头采集时间。普通 UI FPS、插值次数、NPU 利用率均不替代验收。COCO-17 的通过也不等于更完整手部关节能力已通过。

## 5. 决策

继续保留目前同包回退方案。下一轮新增工作的核心应是：**精度合格的 NPU 专用模型候选 + 消除可验证的 I/O 浪费 + 稳定的新帧供给**。缓存责任和原生输出可先离线实现并覆盖异常测试；模型导出/校准与供帧优化共同推进。RGA、多上下文只作为可测候选，不在未确认支持时默认开启。

当前证据足以支持这些方向值得投入，尚不足以证明稳定 20–25 FPS 已实现，也不能严谨地为每个候选承诺增加多少 FPS。本次仅新增研究文档，无代码或 APK 变更。
