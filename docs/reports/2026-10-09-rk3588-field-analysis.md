# RK3588 实测分析与优化（2026-10-09）

## 结论与证据范围

现场会话 `session-20261009-025543-989-14ab4a42` 的主要瓶颈是当前
NCNN Vulkan FP32 模型执行链路。低等级仍约10次新结果/秒；目标25次/秒
需要把完整处理压到40ms左右，同时提高实际输入发布率。
优先验证 RKNN NPU 后端，其次评估精度合格的量化/模型改造。
不能由这些日志认定 RK3588 整体硬件不够、GPU已经满载、或设备过热。

## 当前链路

RK3588_t / Android13 / Mali-G610 / Vulkan，8核CPU、约7.8GB内存。
活动 profile 为 `android-ncnn-vulkan-quality-low`，模型输入512×288、FP32，
完整图每帧执行；没有 RKNN 后端或NPU模型。人数/区域限制不会缩小全图模型。
硬件解码器为 `c2.rk.avc.decoder`，真实解码输入3840×2160；
请求1280×720已经正确限制发布尺寸，但没有改变上游4K码流和解码尺寸。

| 观测 | 实测值 | 解释 |
|---|---:|---|
| 实际输入发布 | 15.33 FPS | 模型加速后还需提高此输入率；可能包含GPU竞争 |
| 完成新结果 | 9.99 FPS | 与98.3ms处理预算一致 |
| 有人窗口骨骼通知中位数 | 9.55次/秒 | 达到20次/秒的窗口占0% |
| 当前结果总耗时均值 | 98.31ms | 单个串行工作者约10.17次/秒上限 |
| 本地结果年龄均值/P95 | 228.57 / 311.93ms | 从本地发布开始计时，不含传感器/网络全延迟 |
| App CPU占全机 | 12.13% | 对8核归一化；约等于单核容量97%，不是CPU完全空闲 |
| App PSS / 可用内存 | 207MB / 4211MB | 无当前内存耗尽证据 |

人物只出现在约16.5%的统计窗口。整段含人体结果通知1.57次/秒不能解释为
“人物在画面时只能识别1.57FPS”。分析器已把人物覆盖率与有人窗口速率分开。
SDK别名 `PoseMs` 在这条YOLO全图路线代表后端整体，并非逐人单独姿态推理。

## 时间花在哪里

以下六段取同一原生帧的83个完整样本。SDK当前结果与稀疏原生样本可能属于
不同帧，不能跨帧相减后声称得到了CPU耗时。

| 原生阶段 | 平均ms |
|---|---:|
| 图像导入/预处理录制 | 0.109 |
| 生产者同步/预处理提交等待 | 6.583 |
| 模型Extractor、内部GPU提交/等待及输出录制 | **85.038** |
| 最后推理/输出提交等待 | 4.981 |
| 完成结果复制 | 0.541 |
| 所有权释放/同步 | 0.949 |
| 六阶段总和 | **98.202** |

模型阶段占86.6%，是首要优化对象；复制结果不是主要瓶颈。
预处理提交等待P95约28.42ms、最大55.36ms，说明输入/GPU同步偶有明显抖动。
85ms是墙钟耗时，包含NCNN内部同步，不是纯GPU运算或纯CPU时间。
旧 `received_us` 是取图时最近一次demux到达观测，不保证对应同一个压缩包；
不能将它与 `decoded_us` 的差称为精确解码耗时。

## 硬件不足还是模型需要优化

目前最有依据的判断是“现有后端、精度和并发负载在RK3588上效率不足”。
一加的同等级模型阶段约33ms、RK约85ms，但前者用视频、后者还处理4K RTSP，
不是完全隔离硬件变量的比较。不能仅凭二者比值建议更换设备。
RK的NPU没有被使用，尚不能判定此硬件的合适加速路径也无法达到目标。

1. 先验证NPU执行链路和正确模型，记录完整处理耗时，不先降低精度标准。
2. 若NPU仍不足，再做INT8/混合精度、模型规模或算子改造；每个候选独立过
   人数、框、关节误差、抬臂、遮挡和时序稳定性对照。
3. Vulkan FP16先前未通过本项目数值门槛，不直接打开该开关。它的失败也
   不等于RKNN非量化/混合精度必然失败；不同后端需要独立验证。
4. 帧间插值不会增加实际新骨骼结果率；不将重复/预测结果计作推理提速。

## 官方资料支持的方向

[Rockchip Model Zoo](https://github.com/airockchip/rknn_model_zoo/blob/main/README.md)
公布YOLOv8n-pose INT8、640×640在RK3588单NPU核55.9FPS，即约17.9ms模型推理。
官方说明该表按平台最高NPU频率测量，通常不含预处理/后处理。
这是NPU值得尝试的强依据，不是本SDK保证55.9FPS，也不是相同权重/精度比较。

[RKNN-Toolkit2官方说明](https://github.com/airockchip/rknn-toolkit2)
要求先将模型转成RKNN，再通过RKNN Runtime C/C++ API调用NPU。
当前调研版本2.3.2；需固定转换器、Android运行库和目标驱动兼容证据。
[官方姿态转换示例](https://github.com/airockchip/rknn_model_zoo/blob/main/examples/yolov8_pose/python/convert.py)
对姿态分支使用混合量化配置，不能只依据检测框正确就接受INT8关节精度。

[官方C API](https://github.com/airockchip/rknn-toolkit2/blob/master/rknpu2/runtime/Android/librknn_api/include/rknn_api.h)
区分AUTO与0/1/2三核mask；AUTO不是自动使用三核。
先测单核和多核同一模型，不把三核当作必然三倍。
`rknn_outputs_get`会等待完成，必须在SDK工作线程调用。
Vulkan AHB不能未经格式、stride、缓存一致性和同步证明直接当NPU输入。
首版允许明确计量的工作线程输入转换/复制，随后验证可行的DMA/RGA路径。

## 已实施的有限优化

现场83417条事件中81181条为原生转存，常规crop/lease/fd/转换逐帧记录约8万条，
且原来同时进入 `events` 与 `native.log`。已完成：

- Android Input常规明细仅首3帧及每64帧记录；错误、重连、codec变化和终态
  资源报告保留。私有资格验证路线仍逐帧完整记录。
- 原生原文只写 `native.log`；`events` 保留批次索引和严重消息，不重复所有明细。
- 记录每次日志flush实际耗时；Mali devfreq自动发现并支持 `72@800000000Hz`。
  负载未开放时仍保留可读时钟；CPU/GPU热区与电池温度分别记录。
- 新Input样本增加 `submitted_us/converted_us`，可分离本地解码观测到提交的
  调度等待与提交到完成轮询的间隔；后者不是纯GPU时间。
- 分析器按真实profile切换分段，不将同一输入上的Medium/Low统计混合。

这些减少确定存在的额外工作；未据此宣称RK骨骼已达到20–25FPS。
SDK原生、FP32模型、V1/C ABI及帧所有权同步协议没有改动。

## NPU模式当前状态

NCNN Vulkan现有模式可运行。NPU模式尚未接通，不提供仅改标签的“可用NPU”。
已有源码中没有RKNN后端或已合格RKNN ModelPack；既有Android构建还严格限制
NCNN同模式profile。双模式接入必须同时覆盖后端、模型、配置、APK依赖和UI。
具体接入/测试顺序见
[NPU接入计划](../plans/2026-10-09-rk3588-npu-acceleration.md)。

本机尝试启动Linux转换环境：Docker报告 `hasNoVirtualization=true`，
WSL2提示虚拟机平台/BIOS虚拟化未启用，无法执行Linux RKNN转换。
仅连接OnePlus，不能运行RK3588 NPU。没有修改系统虚拟化、重启或升级设备驱动。
已提供固定输入哈希、真实校准列表和未验收标记的候选转换工具；其保护性测试
通过不等于已经转换了模型。下一必需产物是Linux上真实转换及数值对照结果。
